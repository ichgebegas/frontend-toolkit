# Перенос категорий из OpenSite

## Цель

Собирать локальную библиотеку блоков, которые быстро переносятся в другие проекты: автономный HTML/CSS/JS, живое preview и визуально точное поведение исходного примера. Менять можно палитру toolkit, но не структуру, ритм и назначение блока.

## Source-First Карта Блока

До верстки каждого блока заполнить короткую карту:

| Поле | Что зафиксировать |
| --- | --- |
| Source | файл компонента OpenSite и открытый live preview |
| Content | точные заголовки, абзацы, labels и CTA |
| Images | URL, aspect ratio, crop и скругления |
| Icons | имена исходных иконок и размер stroke SVG |
| Layout | max-width, columns, gaps, padding, порядок на mobile |
| Typography | font-size, line-height, weight, max-width, `text-wrap` |
| Pattern | имя, фон поверхности, line color/tone, effective opacity |
| States | hover, active, focus-visible, selected/expanded |
| Devices | desktop, tablet и mobile размеры preview |

Нельзя заменять иконки символами вроде `+`, `o`, квадрата или текстовой стрелки. Для vanilla-примера переносится inline SVG с тем же назначением, что и в source.

## Порядок Реализации

1. Найти исходный компонент и сверить его с live preview OpenSite.
2. Снять структуру DOM и ключевые computed styles, особенно для того, что влияет на перенос текста и фон.
3. Сделать автономный `index.html` и `style.css`; JS добавлять только для реального поведения блока.
4. Перенести изображения, иконки, pattern и состояния действий до визуальной оценки.
5. Адаптировать только брендовые токены: grayscale-палитру, accent и focus ring toolkit.
6. Проверить автономный файл напрямую и через detail-view iframe.
7. Добавить блок в каталог только после сравнения desktop и mobile с исходником.
8. После изменений содержимого iframe повысить `previewRevision` в `demo/script.js`, иначе витрина может показывать старый результат.

## Визуальный Контракт

- Иконки совпадают по смыслу и типу: map-pin остается map-pin, phone остается phone, arrow остается arrow.
- Перенос заголовка проверяется не на глаз: сравниваются ширина контейнера, размер шрифта, line-height, max-width и `text-wrap: balance`, если он есть в source.
- Описание и подписи не растягивают композицию и не ломают высоту карточек.
- Pattern проверяется четырьмя значениями: имя узора, фон поверхности, цвет линий и итоговая opacity. Одинаковая opacity не означает одинаковый внешний вид.
- В темной теме оболочки iframe-пример сохраняет собственную тему, если исходный блок не имеет theme-варианта.
- Ни один action не остается без `hover`, `active` и `focus-visible`.

## Browser Acceptance

Для каждого нового блока выполнить:

1. Desktop preview: сопоставить геометрию, перенос текста, media crop, иконки и pattern с OpenSite.
2. Tablet и mobile: проверить перестройку колонок и фиксированные размеры preview без видимого scrollbar.
3. Проверить отсутствие horizontal overflow на 375, 680 и 1365 px.
4. Проверить светлую и темную тему витрины: iframe не должен непреднамеренно менять фон или pattern.
5. Открыть карточку из категории и detail-view; ссылка должна вести на правильный автономный пример.

## Батч Переноса Следующего Раздела

Следующий раздел переносится не целиком вслепую:

1. Выбрать один самый показательный блок категории, например Hero с media и CTA.
2. Полностью пройти Source-First карту и Browser Acceptance на этом блоке.
3. Выделить только подтвержденные общие примитивы категории: media radius, CTA states, pattern token, preview geometry.
4. Перенести остальные блоки небольшим батчем с отдельной картой для каждого, не подменяя их общими догадками.
5. Перед переходом к следующей категории прогнать contract tests и визуально проверить минимум один простой и один сложный блок.

## Лицензия И Источники

Перед публикацией кода, основанного на открытых исходниках, проверить условия репозитория OpenSite и при необходимости обновить `THIRD_PARTY_NOTICES.md`. Публичная витрина должна явно отличаться брендом и палитрой, даже когда логика каталога и композиции изучены по референсу.

## Ошибки About, Которые Нельзя Повторять

Эти проверки обязательны для следующего раздела, потому что именно их пропуск потребовал повторной полировки About:

1. Не собирать блок по одному видимому screenshot. Сначала прочитать компонент source целиком: порядок DOM, отдельные rows, gallery, CTA media и скрытые tab panels. В `About Culture Tabs` ошибка появилась из-за того, что отдельная gallery-строка и CTA images были заменены другой композицией.
2. Не считать совпадение имени pattern и opacity достаточным. Shared `patterns.css` может переопределить локальный token по каскаду. Для каждого patterned block нужно проверить computed `background-image`, итоговый line color и screenshot после подключения общих стилей.
3. Не настраивать headline только визуально на одной ширине. Зафиксировать desktop line count и сверить columns, `max-width`, gap, font-size и line-height. В `About Story Hero` неверные columns одновременно сломали перенос и пропорцию media.
4. Не оставлять source branding в адаптированном примере. До приемки пройти весь текст блока поиском по `OpenSite` и заменить только брендовые mentions на `Toolkit`, сохраняя масштаб соседних logo marks.
5. Не использовать символы как временные иконки. Отдельно искать `->`, `+`, `o`, squares и подобные stand-ins в CTA, lists и metadata. Переносить смысловую SVG-иконку сразу.
6. Не проверять только первоначальное интерактивное состояние. Для tabs, accordion, slider и expandable cards открыть каждое состояние и проверить изображения, тексты, overflow и отсутствие битых URL.
7. Не принимать preview, пока iframe показывает старый кеш. После любого изменения HTML/CSS/JS блока обновлять `previewRevision`, затем перезагружать detail-view и проверять фактический URL iframe.
8. `previewRevision` обновляет URL HTML, но не сбрасывает кеш вложенного `style.css`. При изменении стилей компонента добавлять/повышать query-версию в его `<link rel="stylesheet" href="style.css?v=...">`.

## Source-First Для Новых Разделов

1. Начинать не с визуального приближения, а с конкретного live block на `ui.opensite.dev/blocks/<id>` и соответствующего файла `@opensite/ui/dist/<id>.js`.
2. Снимать из iframe фактические title, description, media URLs, pattern, opacity, responsive-состояния и интерактивное поведение. `registry.js` описывает контракт, но пример в опубликованной витрине может использовать другие данные.
3. Сначала добавлять contract assertions: список блоков, source media id, pattern/opacity, ключевые heading anchors и breakpoint поведения (`lg` для sidebars/split layout).
4. Только после красного теста переносить HTML/CSS/JS. Не подменять source images общим placeholder и не сочинять укороченную структуру longform, если в source она видима.
5. В viewer проверять не только сам компонент, но и ширину iframe: responsive ветка выбирается по внутренней ширине preview, а не по ширине внешней страницы.
6. Снимать desktop, tablet и mobile кадры; проверять скрытие desktop-only sidebar, popover/TOC, pattern contrast, переносы заголовков, скругления media и hover/focus/pressed states.
7. Оставлять attribution и BSD notice при переносе кода или заметных производных из OpenSite.
8. При vanilla-переносе tabs не полагаться только на HTML-атрибут `hidden`: авторское правило вроде `.panel { display: grid; }` может его перебить. Нужен явный `.panel[hidden] { display: none; }` и проверка, что видна ровно одна панель.
9. Проверять responsive-логику управляющих элементов отдельно от контента. В `About Culture Tabs` исходный tab list на mobile является сеткой `2 x 2`, а не горизонтальным скроллом.

## Gate Для Следующего Раздела

Перед массовым переносом Hero или другой категории:

1. Сделать один эталонный блок и добавить contract assertions на его DOM-композицию, SVG-иконки, pattern token/tone и desktop geometry.
2. Снять две пары screenshot: OpenSite/local на desktop и mobile; принять первый блок только после прямого сравнения.
3. Если блок интерактивный, проверить все состояния до начала следующего блока.
4. После эталона перенести не больше трех блоков за один батч и провести такой же browser-check для каждого.
5. Только после зеленых тестов и чистой визуальной проверки расширять батч оставшимися блоками категории.

## Дополнения После Article

Article добавляет не только внешний вид, но и поведение чтения. Для следующих content-разделов обязательны дополнительные проверки:

1. Отличать похожие навигационные варианты по source-коду: `Article TOC Sidebar` скрывает desktop sidebar ниже `lg`, а `Article Compact TOC` использует отдельный раскрывающийся TOC. Нельзя применять mobile-логику одного блока ко всей категории.
2. В каждом блоке с TOC или chapters проверить соответствие `href="#id"` реальным заголовкам документа и проверить активное состояние после прокрутки через `IntersectionObserver`.
3. Проверить sticky только там, где он остается sticky в исходнике; на узком экране sidebar должен вернуться в обычный поток и не заслонять начало статьи.
4. Для long-form blocks сверять не только первый экран, но и тело статьи: ширина prose, интервалы заголовков, blockquote, hero-media и итоговое положение navigation/CTA.
5. В detail-view проверять категорийный breadcrumb после подключения нового раздела. Article не должен открываться с подписью `About`.
6. Для варианта с mobile disclosure обязательно проверить открытие, закрытие, `aria-expanded` и отсутствие горизонтального overflow.
7. Картинки и авторские данные брать из подтвержденных source assets или заменять собственными позже отдельным asset-проходом; не подмешивать случайные изображения ради похожего thumbnail.
